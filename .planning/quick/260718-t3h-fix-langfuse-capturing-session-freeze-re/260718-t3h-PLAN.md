<objective>
Stop session-lifecycle control notices — "Esta sesion se congelo automaticamente por inactividad del creador.", "El creador ha reactivado la sesion.", and the freeze-cap/close variants — from being treated as genuine human chat turns. Today they are attributed to the `user` role in Langfuse traces AND injected into the AI generation context as if a participant said them.

Purpose: Langfuse trace data must reflect what participants actually said; the AI personas must not receive control-plane noise as conversation history.
Output: A proper `system` message role, applied at the insertion sites, and excluded from every message-history loader that feeds the LLM and Langfuse.
</objective>

<investigation_findings>
Root cause (verified, not assumed): the `messages.role` column is
`not null default 'user' check (role in ('user','assistant'))` (migration `0005_reactions_personas.sql`).
The control-notice inserts in `sessions-helpers.ts` (`freezeSession`, `unfreezeSession`, `closeSession`)
do NOT set `role`, so every notice defaults to `role='user'`.

Both angles from the scope clarification were checked — the bug is NOT Langfuse-only:

1. Insertion point — `apps/api/src/lib/sessions-helpers.ts`
   - `freezeReasonMessage()` (lines 83-92) and `unfreezeReasonMessage()` (lines 155-162) produce the Spanish notices.
   - Inserted with `author_id: SYSTEM_AUTHOR_ID` (all-zeros sentinel) + `display_name: 'system'` but NO `role` → defaults to `'user'`.
   - `closeSession` inserts "La sesion ha finalizado." the same way.

2. LLM context, human /invoke path — `apps/api/src/routes/ai.ts`
   - Recent-8 query (lines 214-220) and older/compression query (lines 228-234) both `.select('role, content')`
     and map `role: (m.role ?? 'user')`. Notices (role='user') flow into `recentMessages`/`olderMessages`
     → `promptArray` (line 257) → `initialState.messages` (line 410) → sent to the model.
   - CONFIRMED: they DO reach the AI generation context — this is not excluded today.

3. Langfuse trace — `apps/api/src/routes/ai.ts`
   - The graph is invoked with `callbacks: [callbackHandler]` (line 403) over the SAME `initialState.messages`.
     So the identical polluted array is what Langfuse traces. Fixing the context query fixes Langfuse in one move.

4. Proactive-bot path — `apps/api/src/lib/trigger-engine.ts`
   - `fetchRecentMessages()` (lines 608-630) `.select('role, content')` and feeds `state.messages`
     into the bot graph invocation (line 317), also Langfuse-traced. Line 627 already anticipates a
     'system' role but currently receives role='user', so notices land in the bot context too.

5. Bonus bug fixed for free — `apps/api/src/routes/ai.ts` lines 314-324
   - `lastHumanMessage` filters `.eq('role', 'user')`; a freeze notice can be picked as the "last human
     message", making `lastHumanAuthorId = SYSTEM_AUTHOR_ID` (all-zeros) → wrong participantId for
     moderation/personalization. Once notices are role='system', this query excludes them automatically.

Fix strategy: introduce a proper `system` role (the ProviderMessage type + trigger-engine already
anticipate it), tag the notices at insertion, backfill existing rows, and exclude `role='system'` from
every message-history loader that builds LLM/Langfuse context. The notices remain inserted + broadcast
to the chat UI (MessageList) — participants still see them; only the LLM/Langfuse context is cleaned.
</investigation_findings>
