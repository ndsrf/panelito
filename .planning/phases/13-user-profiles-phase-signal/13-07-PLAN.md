<objective>
Close the PROFILE-02 Truth 2 verification gap (WR-04 + WR-03, both Critical for this truth). Today the D-11 personalization splice (`summarizeParticipant()` appended to Coach/Analyst prompt guidance) only fires when `state.skillMeta?.participantId` is set — which among all Skills only `moderationSkill` ever does, AND its `participantId` is threaded from `config.configurable.participantId = user.id` (ai.ts:368), which the `/invoke` ownership gate forces to ALWAYS be the session creator, never the actual author of the message being responded to. Net effect: personalization is unreachable for non-creator participants and only fires on moderation escalation, never on ordinary facilitation turns. The splice branch also has ZERO test coverage.

Design (three coordinated changes, no new Skill needed):
1. **ai.ts (WR-04):** resolve the actual author of the last human message on the active branch (server-side `messages` query, `role='user'`, most recent) and thread THAT into `config.configurable.participantId` instead of `user.id`. This corrects moderation escalation attribution AND supplies the correct default personalization target. Mirrors how `profileBuilderNode` resolves identity from the authoritative `messages` table (never client/LLM-supplied).
2. **facilitation-agent.ts + analytics-agent.ts:** change the personalization target from `state.skillMeta?.participantId` to `state.skillMeta?.participantId ?? config.configurable.participantId`. Because the Role nodes run whenever a Coach/Analyst Skill wins arbitration (routeAfterTriggerGate) or on the silence_gate proactive path, this makes personalization fire on ordinary facilitation moments (silence-break, drift-redirect, fact-check, phase-readiness, orphan-edge), targeting the participant the turn is responding to — while a Skill that DOES set skillMeta.participantId (moderation) still wins.
3. **Tests (WR-03):** add a test to each Role node's suite that injects a target participant + mock profile and asserts `summarizeParticipant()` text is spliced into the composed system prompt.

Opportunistic non-blocking hardening bundled where the file is already open (do NOT let these block the above; do NOT expand TRIGGER-02's core gate/derivation): **WR-02** (ai.ts: suppress phase_signal when current phase id does not resolve, instead of falling back to phase 0) and **WR-01** (phase-readiness.ts: only advance the M-message counter on the genuine human-message path).

Purpose: Make the ROADMAP's stated scenario ("Earlier you mentioned X — does this support or challenge that?") actually reachable for real participants during normal facilitation, with a test that proves it.
Output: Correctly-attributed, generally-reachable personalization + regression tests + two cheap warning fixes.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client `/invoke` request → participant targeting | The invoker is always the creator (ownership gate); the participant the AI responds to is a DIFFERENT, possibly guest, author. Target identity must be resolved server-side, never taken from the request body or an LLM label. |
| participant-authored message content → LLM system prompt | Profile positions/assertions (user-authored) are spliced into the Coach/Analyst system prompt. |
| resolved participantId → moderation escalation count | participantId keys `increment_moderation_count`; a wrong value would misattribute escalation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-07-01 | Spoofing/Information Disclosure | ai.ts participantId resolution | mitigate | Resolve the target author from the authoritative `messages` table (most-recent `role='user'` on the active branch, path-filtered by `ancestorPaths`) — never from client input or the LLM `speaker` label — so a participant cannot cause the Coach to surface, or target, a profile that is not the actual author's. Residual: the surfaced positions were already stated publicly in the shared chat (low). |
| T-13-07-02 | Elevation of Privilege/Tampering | moderation_count attribution | mitigate | participantId = the server-resolved author of the offending message (self); a participant can only cause their OWN message to be moderated, never inflate another participant's count. RLS (row-ownership SELECT, service-role-only writes) on participant_profiles unchanged. |
| T-13-07-03 | Information Disclosure | summarizeParticipant prompt injection | mitigate | summarizeParticipant already escapes user content via escapeUntrustedText + `<<<PARTICIPANT_PROFILE_DATA>>>` delimiter framing (unchanged, reused) — no new untrusted-content path introduced by widening WHEN it fires. |
| T-13-07-04 | Tampering | phase_signal next-phase resolution (WR-02) | mitigate | Suppress the advance signal when the current phase id does not resolve (findIndex -1), preventing a stale/corrupted `current_phase` from offering "advance to phase 0". |
| T-13-07-SC | Tampering | npm installs | accept | No new packages added (edits + tests only). No legitimacy gate needed. |
